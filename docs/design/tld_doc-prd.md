# PRD: tld_doc.h, live documentation for tld.h and tld_ai.h

Status: built, 2026-11-24, branch `feature/live-docs`. Revised the same day: the
decision-model tier of the first design was removed (section 11).

## 1. Goal

A third single header, `tld_doc.h`, that a C program links in and asks in plain language
about `tld.h` and `tld_ai.h` ("how do I read a JSON string?"). It answers with the manual
entries whose words match the question, ranked and copied word for word, and states
which of the question's words occur in the manuals and which do not. The main user is a
program, or a coding agent, that writes C code against tld and needs exact API facts.

tld_doc.h is a **lookup, not a recommender or a judge**: it finds documentation and
reports the facts of the search. It never writes code, plans or advice, and it does not
claim that the entries answer the question; the reader decides.

## 2. Decisions

| Decision | Choice |
|---|---|
| Where | A third single header `tld_doc.h` in the repository root, next to `tld.h` and `tld_ai.h`. It builds on `tld.h` only. |
| Embeddings | None. |
| Models | None. The answer is deterministic: the same question always gives the same text. |
| Search | A word search with `tld_bpm` (tld.h) over one record per manual entry, ranked by BM25F with its standard parameters (section 7). |
| Off-topic questions | No verdict. The head of the text lists the question's words found and not found in the manuals ("Not found: weather, paris"), so the reader can judge. |
| Output | Plain text written for a coding agent, plus the hits as a C struct. |
| Drift | The corpus inside tld_doc.h is generated from tld.h and tld_ai.h by `tools/tlddoc.c`, by the same command that writes the manuals, and checked by the same ctest (`docs-current`). |

## 3. Non-goals

- Embeddings or any vector search.
- Any model call: no rating, no reworded queries, no text written by a model.
- Synonym lists. The known synonym gaps (section 9) are accepted.
- Module overview entries, stemming beyond the simple suffix rule, writing examples.
  (The general sections of the manuals are records since 2026-11-24, see section 5.)
- tld_doc.h describing itself: its corpus covers tld.h and tld_ai.h only.
- A server, a daemon or any network access.

## 5. The corpus (generated, never edited)

- `tlddoc ROOT` (and `cmake --build build --target docs`) makes, in one run, `docs/tld.md`,
  `docs/tld_ai.md`, `docs/tld_doc.md` and the corpus block in `tld_doc.h`. There is no
  separate step to forget. An output that is already current is not written (no
  needless rebuild); a changed one is written to a temporary file in the same directory
  and renamed over the old one, so a failed run never leaves a half-written header
  (ctest `docs-unchanged`).
- `tlddoc --check ROOT` (ctest `docs-current`) fails when any of the four differs from what
  would be generated. The output holds no dates or paths: byte-for-byte reproducible.
- The block sits between two marker lines, e.g.
  `/* ---- BEGIN CORPUS: generated by tools/tlddoc.c from tld.h and tld_ai.h; do not edit ---- */`
  and the matching END line. Everything else in tld_doc.h is hand-written, and tlddoc
  documents it (docs/tld_doc.md) by the existing comment convention, skipping the block.
- One record per manual entry (one `###` heading of docs/tld.md or docs/tld_ai.md, so a
  family such as the six `tld_json_get_*` getters is one record), holding exactly the
  text the manual shows:
  - the names (all names under the heading, in order),
  - the header (`tld.h` or `tld_ai.h`), the module or section name, and that module's
    one-line description,
  - the declaration block,
  - the doc text (plain text as in the manual),
  - the code examples of the entry, or none.
- After the entries, one record per general section of the two manuals (Usage, Errors,
  Memory, Threads, ...; every section of a header's top comment but the licence), kind
  `TLD_DOC_SECTION`: names `"tld.h: Errors"`, no module and no declaration, the section's
  text and code examples. Without them a reader of tld_doc answers never saw the rules
  that hold for every function (the `ERROR:` label, NULL arguments, who frees what). The
  answer shows one as `SECTION n: tld.h: Errors` with the Matched line, the text and
  the example, and no Header, Declaration or See also line.
- A corpus identifier: a 64-bit FNV-1a hash of the generated block's records, plus the
  `AI_VERSION` it was generated with, returned by `tld_doc_corpus_id()`.
- C string literals as static const data; nothing is allocated to use the corpus.
- An independent check in `unit-doc`: the number of records equals the number of `###`
  entries in docs/tld.md + docs/tld_ai.md plus their general sections (the `##` headings
  with no `###` entry, without Contents, Licence and Index), every entry's declaration
  appears verbatim in its header file, and every section record has its `##` heading.

As built (refinements of the points above):

- `names` holds every name under the heading, so an expanded family heading such as
  `tld_sort_desc_<type>, tld_sort_asc_<type>` gives the 22 real names.
- `module_desc` is `""` for a section that has no description (all tld_ai.h sections).
- `doc` is the doc text without its code examples; `example` holds the blocks the manual
  shows as C, without their common indentation, separated by a blank line (NULL if none).
- The declaration is the manual's, so "verbatim" has the manual's two exceptions, which
  `unit-doc` checks separately: a macro longer than 7 lines is shown as its signature
  `#define NAME(params) ...` (the part before ` ...` must be in the header), and lines
  expanded from `TLD__SORT_HEADER(type)` / `TLD__SHUFFLE_HEADER(type)` need that
  invocation in the header. Every other line must appear verbatim.
- Corpus identifier: `"HHHHHHHHHHHHHHHH-V"`, 16 lower-case hex digits of FNV-1a 64 over
  the records in order, each record's seven fields (names, header, module, module_desc,
  decl, doc, example) as their bytes plus a 0 byte, a NULL field as the byte 1 plus a 0
  byte; then `-` and AI_VERSION. `unit-doc` recomputes it from the records.
- The corpus block lives inside `TLD_DOC_IMPLEMENTATION`, as `tld__doc_corpus`,
  `TLD__DOC_N_ENTRIES` and `TLD__DOC_CORPUS_ID`.
  `tlddoc --out DIR` redirects the manuals only; the block is always written into
  `ROOT/tld_doc.h`. `--examples` covers all three headers (tld_doc.h's examples go to
  `DIR/tld_doc-NN.c`) and writes no corpus block. The macros of the block and of the
  implementation are `#undef`'d at its end, except `TLD__DOC_IMPLEMENTED`.

## 6. Public API (tld_doc.h)

Names follow the repository's naming rules (`tld_doc_*`, `TLD_DOC_*`; internals
`tld__doc_*`, `TLD__DOC_*`). `TLD_DOC_VERSION` is "0.1.0".

```c
typedef struct {
        const char *names, *header, *module, *module_desc, *decl, *doc;
        const char *example;            /* NULL when the entry has none */
} tld_doc_entry;
int tld_doc_n_entries(void);
const tld_doc_entry *tld_doc_entry_at(int i);   /* NULL + ERROR outside 0..n-1 */
const char *tld_doc_corpus_id(void);

typedef struct { const tld_doc_entry *entry; double score; } tld_doc_hit;
typedef struct { tld_doc_hit *hits; int n_hits; char *text; } tld_doc_answer;
typedef struct { int max_bytes; /* 0: 4096 */ int top_n; /* 0: 8 */ } tld_doc_opts;
int tld_doc_ask(const char *question, const tld_doc_opts *o, tld_doc_answer **out);
void tld_doc_answer_free(tld_doc_answer *a);
```

`tld_doc_ask` returns FAIL only for bad arguments (question or out NULL, max_bytes or
top_n negative) or out of memory; `o` NULL means every default. The score is the BM25F
score, plus 1000 for an exact name match and 500 for a close one, so those come first.

## 7. How a question is answered

The rules, as in the comment above the search code in tld_doc.h:

1. Words: ASCII letters, digits and `_`; every other byte separates words. At most 16
   distinct words, each cut to 32 bytes; the head names the first 8 words left out
   ("Not searched: ..."). An identifier contains `_` or is exactly, with case, a corpus
   name (`MMALLOC`, `galloc`, `OK`). Other words are lower-cased; a stopword (a fixed list
   of about 100 English function words) or a word under 3 bytes is dropped. When a word
   comes twice, once as an identifier (`MMALLOC`) and once not (`mmalloc`), the
   identifier is kept, whichever comes first.
2. Stems: a plain word loses one suffix (`ation`, `ing`, `ies`, `ed`, `es` if 4 bytes
   remain, `s` if 3 remain and not after `s`, `u`, `i`), then a final `e` if 4 remain.
   Identifiers are searched whole.
3. Matches: `tld_bpm_find` (TLD_BPM_NOCASE) in five fields per record: names;
   declaration with doc text; example; module name; module description. A match counts
   only at a word start; the number of matches is the word's frequency in the field.
   The two module fields are shared by all records of a module, so they are scored
   without length normalisation (b = 0): they move a module's records together and
   never reorder them.
4. Near matches: a word with no exact or name match anywhere is searched again with
   k = 1 (k = 2 from 12 bytes): first its stem, when it has at least 6 bytes
   ("alocations" -> "alocation", 1 edit from "allocation"); when that finds nothing, the
   word as written, when it has at least 6 bytes and differs from its stem ("alocation"
   stems to "aloc"). Those matches become its frequencies, and the head shows the
   nearest form, the first word of the closest match with its own distance
   ("levenstein (nearest: \"Levenshtein\", 1 edit)"). Trying the stem first keeps every
   typo the stem finds; on 793 generated typos this order loses none and gains 32.
5. Names: an identifier equal to a record's name is a name match; within d edits of a
   name (d <= 3, 6d <= length) a close-name match.
6. Ranking: BM25F with k1 = 1.2 and b = 0.75, the names field weighing 3, the others 1;
   idf = log(1 + (N - df + 0.5) / (df + 0.5)). Name matches add 1000, close names 500.
   Hits are the top_n records with a score above 0, best first (ties: manual order).

BM25F replaced a hand-made weighting of the first design (field factors 30, 15, 3, 2,
1.5, 1, 0.5). It is the standard formula with its usual parameters, no more code, and
it did not do worse on the evaluation set (section 9).

## 8. The answer text

A head, then one block per entry shown, best first:

```
tld_doc answer
Question: how do I read a JSON string?
Words found in the manuals: read, JSON, string. Not found: none.
Entries ranked by word match. Everything under ENTRY is copied exactly from the tld manuals.

ENTRY 1: TLD_JSON_COMPACT
Header: tld.h, module json (the module description, with the first entry of a module only)
Matched: words read, JSON, string        (or: name "x"; close to name "x"; near y)
Declaration:
    ...
Documentation:
    ...
Example: none in the manual.             (or "Example:" and the code)
See also: tld_json_dump                  (corpus names the doc text mentions)

Not shown (byte budget): name; name; ... and N more
```

Instead of the found/not-found line the head may say that the question has no words to
search for; with words but no hits it says that no entry matches them. The text is at
most max_bytes bytes, except that the head always appears whole (at most 2300 bytes) and
so does the shortest Not shown line. Entries come in rank order, each as complete as
fits: the declaration is never cut; the doc text is whole, cut after its last sentence
that fits (" ..."), or "not shown (byte budget)"; the example only with the whole doc
text. The first entry whose declaration does not fit, and every entry after it, is
listed under "Not shown (byte budget)". See also lists names from the doc text only (the
examples name RUN, ASSERT, MFREE everywhere).

## 9. Evaluation

`tests/doc/questions.tsv`, tab-separated `id kind question expected note`: 43 covered
questions (spread over all modules, worded as a user would, with identifiers and typos),
11 partial ones (tld does part of it; expected = the entries for that part) and 15 off
ones (tld does not do it). `expected` is comma-separated and every name must be in the
corpus (`doc-eval-unknown-name` checks this), so a renamed entry cannot turn a question
into a permanent known miss. A note starting `miss:` marks a known miss with its reason;
at most 20% of the covered and partial questions may be marked.

`doc-eval` (ctest) prints, for covered and partial questions, top 1, top 3, top 8,
shown (the expected entry is an ENTRY block at 4096 bytes, not only named) and MRR; for
off questions, how many answers name a word not found in the manuals. It fails on an
unmarked miss (no expected entry in the top 8). With `-v` it prints every question.

2026-11-24, before (hand-made weights) and after (BM25F) on the same set:

| | top 1 | top 3 | top 8 | shown | MRR |
|---|---|---|---|---|---|
| covered (43), before | 28 | 39 | 41 | 38 | 0.77 |
| covered (43), after | 29 | 38 | 41 | 40 | 0.79 |
| partial (11), before | 3 | 6 | 7 | 3 | 0.43 |
| partial (11), after | 3 | 7 | 7 | 7 | 0.44 |

Off questions, after: 14 of 15 answers name a word that is not in the manuals; 2 have
no hits. Marked misses: c14, c36, p04, p06, p10, p11, all vocabulary gaps (measure vs
timer, categories vs labels, mismatches vs edits, classify vs choose, save vs dump,
translate and pdf). A gap seen but not tuned for: "read a JSON string" ranks
`tld_json_parse` 6th, because its entry never says "read".

With the general sections as records (section 5) and ten questions that expect one
(`s01` to `s10`, counted as covered):

| | top 1 | top 3 | top 8 | shown | MRR |
|---|---|---|---|---|---|
| covered (43), sections in the corpus | 29 | 38 | 41 | 40 | 0.79 |
| partial (11), sections in the corpus | 3 | 7 | 7 | 7 | 0.42 |
| covered (53), with `s01` to `s10` | 37 | 47 | 50 | 49 | 0.80 |

Of the ten, eight have their section at rank 1, one at rank 2, and one is a marked miss
("compile" where the section says "Build"). The partial MRR moved from 0.44 to 0.42: in
`p05` a section now ranks above the expected entry.

## 10. Tests and consistency

- `docs-current`: the manuals, docs/tld_doc.md and the corpus block are current.
- `docs-unchanged`: on a copy of the headers, a second tlddoc run writes nothing, an
  edit rewrites the outputs whole and keeps the file mode, and a failed write leaves the
  old file and no temporary file.
- `unit-doc`: the corpus against the manuals and headers (section 5), the corpus API, the
  search on fixed questions (identifiers exact, with a typo, without `_`, `OK` against
  `ok`; typos through the stem and as written, and their nearest forms; a word repeated
  in two spellings; found and not found; no words; no match; top_n; the same text
  twice), every text
  checked for the rules of section 8 (budget, head, entries a prefix of the hits with
  the rest under Not shown, whole declarations and examples, cut doc text, See also
  from the doc text, the module description once per module) over 738 budgets, and
  edge cases (empty, stopwords, long questions, bytes >= 0x80, control bytes, bad
  arguments).
- `doc-eval` and `doc-eval-unknown-name` (section 9).
- `null-args-doc` (every tld_doc function; `covered.sh` fails when one has no case), the
  `doc` scenario of `oom-tld`, `tld_doc.h` in `names` (what it adds to tld.h is
  `tld_doc_`/`TLD_DOC_`), `doc-examples-doc`, `tld-ask-run`, `single-header-doc` and
  `single-header-doc-strict` (`-std=c11 -Wall -Wextra -pedantic -Werror`).
- ASan clean; all of ctest passes on macOS clang and Linux gcc.

## 11. History: the decision-model tier, removed

The first design added a tier 1: the decision model (autotrust-jev, through
`ai_rate_dyn` of tld_ai.h) rated each retrieved entry on 6 levels, and the answer carried
a verdict (COVERED, NOT COVERED, UNCHECKED) with the kept and rejected entries. It was
built and tested against the mock server. Run against the real model, its ratings were
flat (mostly levels 1 and 2 with confidence below 0.2), and it marked "how do I read a
JSON string?" NOT COVERED. A verdict also claims more than a lookup can know, and any
threshold on it would have been tuned to this question set. The tier was removed: no
tld_ai.h dependency, no verdict, and the head states the facts of the search instead.
